# Authentication design and threat model

## Trust boundaries / STRIDE

Assets: password hashes, JWT signing key, active-account and role records, controller operations, readings, applicant PII, SMTP credentials and audit evidence. The browser, all request bodies/headers, and localStorage are untrusted. The FastAPI process and its private SQLite file are trusted. The relay/ESP32 network is a separate trust boundary. Database/OS administrators can change the database or drop triggers; application controls cannot resist full host compromise.

| STRIDE | Concrete attack | Implemented defense / remaining boundary |
|---|---|---|
| Spoofing | Guess a PIN, reuse a token, impersonate an applicant | Argon2id password login; no legacy PIN/OTP routes; approval required; exact expiry and shared persistent jti denylist |
| Tampering | Edit JWT algorithm/claims, inject role/status into signup, race review requests | Only HS256/at+jwt accepted; required issuer/audience/date/subject/jti checks; strict DTOs and DB CHECKs; BEGIN IMMEDIATE review transaction |
| Repudiation | Deny approving, rejecting, promoting or suspending someone | Transactional actor/target/action/before/after/UTC audit; append-only triggers; administrator-only read API. Off-host export is still required for host-compromise resistance |
| Information disclosure | Steal passwords/tokens, enumerate users, read streams without login | Generic login failure, dummy verification for missing users, redacted validation errors, memory-only origin-bound browser token, scoped API access and stream checks. HTTPS/WSS deployment remains required |
| Denial of service | Exhaust Argon2 memory, hammer login, lock known accounts, flood signup email | 16 KiB request bound, two concurrent hash operations per process, persistent IP/account windows, signup cap, bounded SMTP batches. Distributed floods and targeted account-lockout abuse still require gateway/operational controls |
| Elevation of privilege | Self-approve, forge admin role, retain access after demotion | Signup sets pending/NULL; only DB-current active sysadmins review; no roles in issued JWT; database lookup every protected request; admin writes reauthorize inside their transaction |

## Choices, alternatives and rationale

- **Storage:** existing SQLite file, with separate connections for auth transactions and new `auth_*` tables. Denylist rows carry absolute `expires_at = token.exp`; remaining TTL is `exp - now`. Expired rows are removed on login/logout; their presence never extends a token's life. Counters are also stored in SQLite, so restart or another worker cannot erase them. Redis TTLs with PostgreSQL users/audit are the distributed alternative. SQLite must be on local disk, not NFS; keep a single controller API deployment. Failures to read auth state fail closed.
- **Password hashing:** argon2-cffi `RFC_9106_LOW_MEMORY`: Argon2id v19, 65,536 KiB, t=3, p=4, 16-byte random salt, 32-byte output. A `needs_rehash` wrapper calls the library's `check_needs_rehash` on successful login. Alternatives benchmarked are 64 MiB/t=4 and 128 MiB/t=3. RFC's first recommendation (2 GiB/t=1) does not fit the chosen 128 MiB concurrent hashing budget. The report measures this workstation, not the target Pi; repeat on the target and assess throughput before deployment. [RFC 9106 §4](https://www.rfc-editor.org/rfc/rfc9106.html#section-4), [argon2-cffi parameter guidance](https://argon2-cffi.readthedocs.io/en/stable/parameters.html), [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- **Passwords / identifiers:** 15–128 Unicode characters, no truncation, case changes or composition requirements on passwords. Email identifiers are validated and casefolded by explicit policy. Names are limited to 100 characters and reject control characters. A breached-password corpus, MFA and password change/recovery are not included; the old mock recovery has been removed rather than reused.
- **JWT:** HS256 only, with a required base64-configured key decoding to at least 32 random bytes; no fallback key. Access-token header `typ=at+jwt`; reject other header fields, including attacker key URLs. Required `sub`, `exp`, `iat`, `jti`, `iss`, `aud`. Integers for dates; exact 1800-second lifetime, no clock-skew leeway. Random UUID subject/jti. Neither role nor status is issued or trusted as a token claim. Ed25519/RS256 plus externally managed public-key rotation is an alternative if verifiers become separate services. Keep a synchronized UTC system clock. [RFC 7519 §4.1](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1), [RFC 8725 §3](https://www.rfc-editor.org/rfc/rfc8725.html#section-3).
- **Session storage / browser:** in-memory, bound to the issuing API origin. Reload signs out locally; explicit logout awaits successful server revocation before reporting success. No refresh token. Parallel sessions are permitted; logout revokes only the presented jti. HttpOnly Secure SameSite cookies plus CSRF validation are the alternative. Memory storage reduces persistence, but XSS can still act as the logged-in user. API origin changes require a new login; HTTPS is required for non-loopback addresses in the login UI.
- **Login defenses:** reserve an attempt atomically before expensive verification. Five attempts per normalized account in a 15-minute window; failed attempts remain, successful login resets that account's counter. Thirty attempts per client IP per 15 minutes; ten signups per IP per 15 minutes. Fixed windows start at first attempt, do not extend indefinitely, and apply to nonexistent accounts too. Unknown/wrong/inactive/locked/throttled login all return 401 with the same message. Saturated hashing returns a non-account-specific 503. Raw spoofable X-Forwarded-For is ignored; uvicorn proxy parsing is disabled. Behind a reverse proxy, all requests may share its IP until explicit trusted-proxy handling is configured. Per-account locking still allows malicious targeted lockout; MFA/adaptive throttling is the alternative for larger deployments. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
- **Review:** successful signup commits a pending/role-NULL user, an audit event and an outbox notification together. Duplicate signup returns the same 202 without extra notifications. Signup before seed is unavailable. Approve assigns exactly worker/sysadmin and activates; reject sets rejected/NULL. Role changes and suspension/reactivation only apply to already approved users. Concurrent competing reviews serialize. The last active sysadmin cannot be demoted/suspended. SMTP notice is not an approval link; reviewers must sign in.
- **Notification:** durable SQLite outbox, addressed to active sysadmins at signup and containing applicant email/name. Verified TLS SMTP on port 465 with authentication; no insecure/plaintext fallback. Background polling every 30 seconds; failures retry after a 60-second claim. At-least-once delivery means a crash after send/before acknowledgement can duplicate a notice. An in-app pending queue is always available. A transactional mail API is the alternative. No SMTP credentials were provided, so real delivery is **not verified**; fake SMTP tests validate message contents, TLS configuration, successful acknowledgement and retry persistence.
- **Audit:** approval/rejection/role/status decisions commit with their event, or both roll back. Records contain IDs, action, JSON before/after status/role, UTC epoch timestamp; no password/hash/token. DB triggers reject UPDATE/DELETE and the API exposes no modification route. The controller's clear-logs route clears readings only. Off-host immutable storage is the alternative for stronger evidence. Full login-failure/authorization-decision logging and SIEM correlation are not implemented.
- **Authorization:** active workers can read/control the shared controller and readings; sysadmins additionally manage users, read security audit and delete readings. There is one controller/tenant, not per-user data ownership. All HTTP protected routes use the central DB+denylist dependency. WebSockets require a bearer first frame within five seconds (never a query-string token), restrict browser Origin, recheck every outgoing frame and recheck idle sessions each second. No protected data is sent before verification. Role/status changes apply to the next authorization decision; requests already in flight are not retrospectively undone. [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).
- **Bootstrap:** local `auth_cli.py seed-admin` prompts with getpass, validates the same signup policy and commits a singleton bootstrap marker with the first admin. Refuses subsequent use even if an account is later altered. No HTTP seed route. Lost all-admin credentials require an audited operator recovery procedure; no hidden reset endpoint exists.
- **Deployment boundary:** signing/SMTP secrets are environment-supplied; DB mode is 0600. Use a private service directory, protected backups, HTTPS/WSS reverse proxy, configured CORS origins and firewall rules. FastAPI defaults to loopback. Explicit LAN configuration is not an HTTPS deployment. The ESP32 firmware still exposes its own API and the Shelly hardware still needs isolation/authentication. The browser's direct-relay fallback and public Next push relay are retired. This implementation does not claim to secure independently reachable hardware.
